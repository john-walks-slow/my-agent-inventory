# 输出风格与核心编码实践

> 全局指令 `~/.dsh/AGENTS.md` 原文同步。

## 输出风格

## 简洁执行

- 语言简洁、清晰、务实。
- 一句话能说清楚，就不要说三句话。
- 根据已知信息可并行的工具调用，优先并行执行，仅在有依赖关系时串行，降低迭代轮数。
- 执行过程透明化，在一组工具调用之间像写 Jupyter notebook 一样注明每阶段摘要。

## Research First

充分的搜索和调研能帮助你避免陷入误区，了解当前 best practice 和事实基准。

任务执行过程中，一旦涉及到与外部事实相关的活动（如：了解库的用法、设计最优实践、探索 sota 等）和任何程度的疑虑（不确定某一事项理解是否准确；不确定做法是否 canonical），总是先进行搜素调研，直到你充分了解对当前任务有助的信息时才继续行动。

搜索前必须参考 /web-search-best-practice。简单搜索在父会话进行。对特定主题的深入调研使用 /spawn-deep-researcher。

## 展示媒体

使用 markdown 图片语法向用户展示图片，路径必须为当前工作区的相对路径：

```markdown
![evidence](<relative/path.png>)
```

以下场景请附图：

- 请用户验收，附上端到端测试中的实际截图。
- Bug 排查，附上对用户判断有帮助的证据。

同理，使用 markdown 链接展示文件：

```markdown
[验证文档](relative/path.md)
```


# 核心编码实践

## 降低认知负荷

- 编写不需要注释就能读懂的代码。注释留给业务背景和特殊备注。
- 遵循单一职责：一个函数只做一件事；一个类只履行一种角色；一个文件只负责一个能力。代码臃肿时，及时拆分。

## 童子军法则

- 离开营地时，要让它比你来时更干净。
- 开发过程中随时重构，防止技术债务积累。注意到代码坏味道时参考 /bad-smell 及时处理。
- 顺手修复废弃变量、拼写错误和格式不整齐的代码。
- 不要轻易使用 hack 和 walkaround。遇到困难时参考 /unstuck 寻找正面解决方法。

## 实用主义

- 用简单直接的方法解决问题。
- 本项目是由我独立开发和管理。将项目规模限制在可控范围，并且尽量采用 canonical 做法。
- 对于大多数异常，**不要**考虑失败降级策略。只需给出错误提示即可。
- 项目真实上线前不要考虑兼容性/旧版迁移；不要写用不到的过度防御性代码。当代码修改没有达到预期时，**先撤销无效修改** 再执行后续修改。

## 防止过拟合与中性克制

- **不要在面向用户的文案里显式强调机制**：用户提出的实现偏好（如“当场抓取而不是内置”）是底层机制要求，不要机械化地变成产品界面上的口号（如“当场抓取并载入”）。界面文案应符合最基础、通用的产品语感（如直接用“导入”）。
- **不要把对话沟通中的临时背景搬进代码和注释**：代码和注释只记录业务真实逻辑与必要上下文，拒绝自嗨式、机械复述用户意图的过度修饰与废话注释。
- **保持平常心，保持中性和简洁**：避免“用力过猛”的迎合式设计。不要因为用户提出某项诉求就只盯住该词汇不放，用成熟、自然、克制的产品与工程语言做交付。

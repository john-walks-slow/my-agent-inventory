# delay-validation

遵循原本的任务要求和工作流，但对于所有原本需要用户确认、验证、授权的步骤——方案选择、计划批准、确认进入下一步、验证通过后再继续、代码提交上库等——**不再停下来等用户**：自行采取最佳判断，立即在指定文档记录，然后继续推进到下一步。高风险项除外。自动推进的范围由可选参数 stopBefore 界定（见下节）。

> 本 skill 计划在将来替换 full-auto。与 full-auto 的区别：不询问 auto_human 子代理模拟审批，由你直接判断，用留痕代替审批——每个决策记录在案，用户事后审阅。

## 可选参数 stopBefore

`/delay-validation stopBefore: <阶段名或自然语言描述>`，不设置时自动推进到任务收尾。

- **语义**：到达该阶段**之前**的一切确认点照常自动决策并记录；**进入该阶段的第一步前停下来**，恢复为询问真实用户——给出至今的决策摘要与待决问题，等用户真实输入。用户在停止点给出输入后，自动推进继续生效，直到收尾（同一 stopBefore 不重复触发）。
- **取值**：当前任务所遵循工作流的阶段名（大小写、中英文均可）：research / plan / align（workflow-research-plan），implement / test / review / validate / documentation / commit（workflow-implement-review），push 等后续动作；或自然语言描述的停止点（如"部署上线前"、"发布到生产环境之前"）。
- **自然语言取值**：按最佳判断映射到最近的阶段或停止点，并把该解释作为「延迟决策记录」的第一条记录（用户审阅时可否决）。
- **不会出现的阶段**：若描述的阶段在本任务中不适用，视为未设置，自动推进到收尾。
- **与高风险项的关系**：两者独立。未到 stopBefore 之前命中高风险项仍立即停下来问真实用户；到达 stopBefore 停止点后即使不是高风险也停。

## 决策标准

- 按"用户在场时你会推荐什么"来决定，而不是选最省事的选项；优先可回退、符合项目惯例的方案。
- 缺少信息时先调研、合理推断，选合理默认值并记录；仅当真阻塞（无法推断且无法绕过）才暂停询问。
- 不因"反正有留痕"而降低决策质量。

## 高风险项（仍必须停下来问真实用户）

- 现有规则明确要求显式/书面同意的：`git stash/checkout/restore/reset --hard`、重启 dsh 线上实例（/restart-dsh）等。
- 不可逆或破坏性：删除/覆盖不可恢复的数据、force push、改动受保护分支。
- 影响共享环境或其他 agent：重启/变更在跑的线上服务、改动他人正在使用的环境。
- 真实世界副作用：登录/验证码/2FA/实机操作（用户负责，不硬搞）、任务未明确要求的对外发布/部署/通知、产生额外费用。
- 安全敏感：提交或暴露密钥、凭据。

## 记录位置

一份文档同时承载延迟决策与待验证项：

- 需求开发：`{project_root}/docs/features/yymmdd-{feature_name}/yymmdd-{feature_name}.validation.md`
- 问题修复：`{project_root}/docs/issues/yymmdd-{issue_name}/yymmdd-{issue_name}.validation.md`
- 其他任务：`{project_root}/docs/delayed-decisions.md`，按 `## yymmdd {任务名}` 追加分节

文档在第一个延迟决策发生时创建（目录不存在则一并创建）。每做一个决策**立即追加一行**，不事后补记。工作流的验证关口（如 /workflow-implement-review 的 Validate 步骤）同样不等待：写好验证项后直接继续 Documentation、Commit（提交仍遵循 /commit-own-changes；若 stopBefore 截止在更早的阶段则先停，见「可选参数 stopBefore」）。

## 记录格式

验证项部分与 /update-validation-requirements 为同一份文档：格式与更新规则一致，保留用户已填写的实际结果、状态、备注与证据。若该文档已由 /update-validation-requirements 创建，保留其结构，追加"延迟决策记录"章节即可。

```markdown
# {feature_or_issue_name} 延迟验证记录

## 验证说明

- 验证对象：{本次交付的功能或修复}
- 环境/前置条件：{设备、系统、账号、数据等；无则写"无"}

## 延迟决策记录

| # | 环节 | 原本需要确认的问题 | 采取的决定 | 依据/理由 | 状态 |
|---|------|--------------------|-----------|----------|------|
| 1 | 计划批准 | 是否按 xxx.plan.md 开始实施 | 批准实施 | 计划无阻塞问题，改动可回退 | 待确认 |

状态：`待确认` → `已确认` / `需调整`。

## 验证项

| 验证步骤             | 预期结果               | 实际结果 | 状态   | 备注/证据 |
| -------------------- | ---------------------- | -------- | ------ | --------- |
| {清晰、可重复的步骤} | {可观察、可判断的结果} | {留空}   | 待验证 | {留空}    |

只记核心场景与必须实机验证的场景（状态沿用：`待验证`、`通过`、`不通过`、`受阻`）；没有则写"无需额外用户验证"。

## 验证结论

待验证。

## 待跟进

无。
```

## 收尾与事后审阅

- 任务收尾时输出简短总结：给出记录文档路径、待确认决策数与待验证项数，请用户有空时审阅。
- 用户审阅后逐条确认或否决，更新"延迟决策记录"状态列；被否决的决策与不通过的验证项按正常流程调整或回退（必要时 /workflow-troubleshoot）。
